§0bThe sidebar — three nav panels & a live preview pane §2 sidebar

The left column has two halves. The top stacks three navigation panels — TABLES, VIEWS, MACROS — every catalog object in one place, click-to-expand for columns or source. The bottom is the preview pane: a live data grid for whatever the user just clicked, with column sort, per-column filter, and an editable SQL line above the grid for one-off rewrites. The preview pane is where most ad-hoc "let me just look" interactions happen — and any query that turns out useful gets promoted to a real cell with one button.

Once a .jfr is loaded the sidebar gains a fourth panel, RECORDING, pinned above TABLES (covered in §0c.3 and §4b). It is hidden until a recording is attached, so the empty-state and the steady-state shapes differ. Everything else in this section describes the three always-present panels and the preview pane below them.

The cyan chip promotes the current preview state — including the rewritten SQL with sort and filters baked in — to a new SQL cell at the end of the notebook. 0b.3 Why this shape

The catalog and the exploration surface are the same column, top-to-bottom. The user finds a table or view by name, clicks once to inspect it, narrows it with sort and filter, edits the SQL when the UI runs out of expressiveness, and promotes the result to a cell when it earns its keep. Every step takes one click or one keystroke; nothing jumps the user into a different pane or a modal. The notebook stays empty until the user decides something is worth keeping.

§0cJFR ingest — from .jfr to queryable tables §3 plan · §IT18.10

The notebook is empty until a recording is attached. Three attach paths: drag a .jfr file onto the page, click Attach recording in the empty state, or paste a URL the worker can fetch. The worker parses the binary, materializes one DuckDB table per event type, and surfaces the parsed schema in the sidebar (§0b). The user sees a progress overlay, a per-event-type row count as it streams in, and a metadata card the moment parsing finishes.

0c.2 Parse progress

Parsing is incremental. The worker reads the JFR chunks in order; each chunk contains one or more event types, and as a chunk completes its events are inserted into the matching DuckDB table. The overlay shows a chunk-level progress bar (total chunks known after the first header), plus a live event-type list that grows row-by-row as new tables come online.

A cell that runs against a partially-loaded recording shows a small ⏳ ingest in progress · 25% chip next to its result count, and re-runs automatically when the ingest finishes. This lets the user start writing queries against the early-arriving tables (gc_pause, cpu_load) while the heavy ones (allocation samples) keep streaming.

0c.6 Why this matters

The 30 seconds between “user drops a recording” and “user sees their first plot” is the moment the notebook either earns trust or loses it. A progress bar that goes from 0 to 100, a metadata card that confirms the file is what they thought it was, and the ability to start querying while the heavy event types still stream — those three together make the tool feel fast even when the underlying parse takes 30 seconds. The capture-guidance drawer covers the user who arrives without a .jfr file at all.

§0dSave, autosave, and persistence §IT12.7 · §IT18.11

The notebook is a real .notebook.md file on disk. Nothing happens inside an opaque IndexedDB blob; everything the user types lives in plain markdown that can be diffed, version-controlled, and read with cat. Three writes need to persist: the markdown source, the workspace state ($$-globals, theme, open tabs), and the parsed JFR cache. Each has a distinct path.

0d.1 The three storage destinations

WhatWhereLifetime
The .notebook.md fileOS filesystem via the File System Access API (Chrome/Edge) or download-on-save fallback (Firefox/Safari)Forever, on disk, under user control
Workspace state (theme, $$-globals, open tabs, recently-opened files)localStorage under key jfr-notebook/workspacePer browser profile until cleared
Parsed JFR cache (DuckDB tables)OPFS (Origin-Private FileSystem) — content-hashed by the JFR file's SHA-256LRU-evicted at 5 GB total; explicit “clear cache” in settings

0d.2 The save model

Autosave is on by default with a 2-second debounce after the last edit. The unsaved-changes state is reflected three places: a small dot on the active tab (§1b.6), the ● chip in the status bar, and the document title prefix (● gc-pauses.notebook.md). The dot clears the moment the file handle's writable.write() resolves.

status bar · save lifecycle

0d.3 Crash recovery

A second debounced write (every 5 seconds, separate from the disk save) goes to localStorage under jfr-notebook/draft/<file-id>. On tab close, browser crash, or unhandled exception, the draft survives. The next open of the file checks the draft's timestamp against the on-disk file: if the draft is newer, a banner offers recover · discard · open side-by-side. Drafts older than the on-disk file (file was saved through another route) are silently dropped.

0d.4 External edits & conflicts

The File System Access API exposes a FileSystemHandle that the runtime polls every 3s with getFile().lastModified. If the disk timestamp moves ahead of the last-written timestamp the notebook holds, autosave pauses and the red-bordered conflict card opens. Reload disk version blows away in-memory edits (with a confirm prompt); keep mine bumps the file's mtime by re-writing; open diff spawns a side-by-side view with the on-disk version on the left.

0d.5 What is not saved

  • The activity feed (§10a.2) — session-only by design.
  • The parsed JFR's DuckDB tables — those are derived from the recording file and rehydrated on open.
  • Plot brush/zoom/hover state, unless the user explicitly shared the URL (§10). The notebook's natural state on open is "no live var set"; the user is expected to gesture again.
  • Chat messages from the agent panel — those are saved per cell in the cell's last_ai_session: frontmatter, not in a separate file (§7b.4).

0d.6 Why this matters

A user who has to type one cell of SQL before they know whether their work will survive a tab close will not commit to the tool. Making the file on-disk and visible — with a clear unsaved dot, a debounced autosave, a recover-on-crash safety net, and an explicit conflict resolution when the file changes underneath you — turns the notebook from a sandbox into a real document the user can trust enough to put effort into.

1a.8.1 Why no Run-above / Run-from-here?

The dep graph already knows what each cell depends on. A linear "run from here downward" sweep re-runs cells that don't need re-running and skips cells that do (if they're listed above but stale). The principled equivalents — Run all upstream of #N / Run all downstream of #N — are available from the dep-graph overlay by right-clicking a node. They cost no UI in the cell column; they live where they're discoverable in context.

1a.8.2 Disabled cells in compare & export

Disabled cells are still part of the notebook — they're saved, they survive serialization, they're visible in the markdown source with their disabled: true frontmatter. Two render-mode interactions:

  • Report mode (§3c.4): disabled cells are hidden entirely. The author keeps them around as work-in-progress; the reader never sees them.
  • HTML/PDF export (§1a.6): disabled cells are skipped in the rendered output. The on-disk markdown still has them.

A common workflow: when investigating a hypothesis, the user accumulates 3–4 exploratory cells that are noisy or slow. Disabling them keeps the work visible for later but stops them re-running on every gesture. The user toggles them back on when they want to revisit.

§1bGetting around §IT12 · §IT18

A notebook that has 30 cells, 15 vars, and a dozen materialized views needs more than keyboard-arrow scrolling. Six everyday motions: rename a cell, find a phrase across cells, edit frontmatter, reorder cells, switch themes, switch notebooks.

1b.1 Rename cell

Each cell has a stable alias (the line-2 chip #3 · gc_overview) that other cells reference. Renaming the alias is a refactor: the editor finds every FROM gc_overview, $gc_overview.brush, cross-cell view reference, and chat-history mention, then offers a single-step rewrite.

1b.3 Frontmatter editor

Frontmatter is YAML at the top of each cell (and the notebook). The editor renders it as YAML with two extras: autocomplete on every known key (pinned, hidden, autorun, deps, materialize, …), and a floating fields button that opens a compact form view for the known keys.

1b.4 Reorder cells

Each cell has a drag-handle on the gutter (the small ⋮⋮ next to the #N chip). Drag picks up the entire cell (all blocks) and shows an insertion bar where it will land. The drop reflows the display indices (the #N is display-only; aliases stay put). Cells with autorun: true that depend on each other are reordered logically, not just textually: a re-run sweep follows the drop. Pinned cells (§IT18) refuse to move into a position that would put them after a non-pinned cell; the cursor turns into a 🚫 chip with the tooltip “pinned cells stay at the top.”

1b.7 Formatting preferences — time, units, locale

JFR data is unit-heavy: timestamps in UTC, durations spanning nanoseconds to seconds, sizes in bytes spanning B to GiB. 1b.7.1 Per-plot / per-column overrides

Workspace preferences set the default; individual plots and columns can override. The plot DSL accepts | format: { x: "time-relative", y: "bytes-binary" }; a result table column can be reformatted in place via right-click → format as · ms / s / auto. Overrides set on a plot serialize into the cell source; overrides set on a table column are session-only (table formatting is a view, not a transformation).

1b.7.2 The "auto" unit policy

auto on durations picks the unit that gives the median value at least one digit before the decimal: 0.7 ms shows as 700 μs, 42 ms stays 42 ms, 1.4 s stays 1.4 s. The choice is made per-series, so a heatmap with values spanning multiple orders of magnitude stays in a single unit (the median), with the legend label noting it. auto on byte sizes prefers the binary suffix family (KiB/MiB/GiB) because that's what the JVM reports.

1b.7.3 Why this matters

A user in CET opening a UTC recording with default settings sees 8:14 GC events and assumes morning — but the recording is from 09:14 local. Without timezone control, every shared notebook is a coordination hazard. The single workspace preference, surfaced visibly in the Formatting card with a live preview row, removes that hazard for the common case.

The match-highlight uses the accent color (--accent); when reduced-motion is set, the highlight is solid; otherwise it's a 200ms fade-in per character.

Universal liveness — every $x is reactive

Every reference subscribes to its variable. Brush a region on cell #1 and every downstream cell that reads $gc_overview.brush re-runs against the new range. Hover a flamegraph frame and every WHERE thread_id IN $flames.hover.category updates. Scoping by name — no scope: clauses

Two panels both binding link-x: $timeline_zoom are coupled because they share a name. Two panels binding link-x: $gc_zoom and link-x: $alloc_zoom are independent. Group membership is implicit in the variable name (the name itself is always explicit). The master and clamp modifiers describe how this panel participates in the shared variable, not what other panels share it.

Three-cell mini example

Frontmatter declares persistent state. Cell #1 brushes; cell #2 reads it. The first variable persists across reloads (in vars:), the second is created on first gesture and lives only for the session.

§3dMacro authoring — the macro fence §6 plan · §IT18.12

Macros are reusable SQL expressions. Pearl example: a percentile(col, p) expression used in five cells, defined once. The notebook gives macros a first-class cell surface — a dedicated ```macro name(args) fence, parallel to ```view name. Macros are visually distinct from views (which materialize rows) and from regular SQL cells (which produce results), and the sidebar MACROS panel lists them all with their signatures.

3d.1 The fence

### #5 · gc_p95 — uses the macro

Diff queries get a one-line DIFF() helper that joins matching rows and shows deltas.

4b.3 The DIFF() macro

A built-in SQL macro joins matching rows between primary and baseline and computes deltas. It is a thin wrapper over a window-aligned JOIN, but it removes 20 lines of boilerplate from the most common comparison shape: 

SELECT * FROM diff(
  primary  := "SELECT cause, count(*) c, avg(duration_ms) d FROM gc_pause GROUP BY 1",
  baseline := "SELECT cause, count(*) c, avg(duration_ms) d FROM baseline.gc_pause GROUP BY 1",
  key      := ["cause"]
);
-- result columns: cause · c_primary · c_baseline · c_delta · c_pct ·
--                        d_primary · d_baseline · d_delta · d_pct

Renders as a result table with a heatmap on the _pct columns (green for improvement, red for regression). The diff macro is the building block; the agent uses it implicitly when asked “what changed?” across two attached recordings.

4b.4 Live coupling across recordings

Brushing on the primary writes its $<cell>.brush as usual; a panel reading from the baseline can filter on it (the SQL names the producer explicitly, e.g. IN $primary.brush). The runtime aligns the brush range using startTime_rel by default — so brushing the first 5 minutes of primary filters the first 5 minutes of baseline, not the same wall-clock instant. An explicit | brush-mode: wall-clock on the consumer panel switches to literal timestamp matching.

4b.5 Why this matters

Without first-class compare, the JFR-Notebook user falls back to opening two browser tabs and eyeballing two charts side by side. Native compare with shared brush, aligned x-axis, and a DIFF() macro turns "did it get worse?" from a multi-step manual process into a three-line query.

5.2 The IN $producer.live-var operator

Every live-coupling binding names its producer. There is no "most-recent" fallback, no anonymous channel — a consumer that does not name its producer is a parse error. §5aChains, composition & saved filters §7.1 · §7.2 · §7.3 · iter-7

A single filter_from chip is the atom. Real notebooks build chains of them: cell A brushes; B filters on A; C joins B with a static threshold; D pivots C by category. Iter-7's job was to make these chains transparent — composable, debuggable, and visible without opening the dep graph.

5a.3 Stale propagation across the chain (plan §7.2.1)

When #1's brush changes, the runtime needs to re-run the chain. The order is determined by the dep graph: #1 → #4 → #9 → #12. Stale propagation works as a wavefront:

  1. Brush gesture on #1 writes $gc_overview.brush.
  2. Every downstream cell with a live-var edge to $gc_overview.brush gets ● stale status (purple dot).
  3. Push-down means #4's narrowed view re-runs first; on success, #9's FROM long_pauses picks up the new view automatically.
  4. Cells render in dep order — no cell renders with mismatched-version data.
  5. If any cell in the chain errors, all downstream cells stay ● stale with a blocked-by badge pointing at the failed ancestor.

5a.5 Predicate push-down across the chain (plan §8.4)

A naive evaluator runs #1, then #4 filters #1's full output, then #9 reads from #4. With a long chain and a tight brush, that's a lot of intermediate rows. The runtime pushes the brush predicate up to the source query:

Without push-down
-- #1 reads 5M rows
SELECT * FROM gc_pauses;

-- #4 filters #1's output
SELECT * FROM gc_pauses
WHERE startTime IN $gc_overview.brush;
-- > transfers 5M rows from #1 to #4
With push-down
-- #1 also gains the brush predicate
SELECT * FROM gc_pauses
WHERE startTime IN $gc_overview.brush;
-- > #1 produces only 50k rows

-- #4 sees only what #1 emitted
SELECT * FROM gc_pauses
WHERE startTime IN $gc_overview.brush;
Iter-9 §9.1 caveat — push-down changes the source cell's output
The runtime is changing what cell #1 produces, not just speeding #4 up. If the user is looking at #1's plot expecting the full 5M rows, push-down is surprising. Resolution: a ↓ push-down chip appears on the source cell head when active, with hover-popover showing which downstream cell added the predicate. One click on the chip disables push-down for that cell (worth it for debugging; loses the perf win).

The completer parses the partial SQL with a forgiving DuckDB grammar and identifies the current slot: select-list · table-ref · join-cond · where-pred-lhs · where-pred-rhs · group-by · order-by · having. Each slot whitelists which sources contribute. A WHERE right-hand side, for instance, surfaces vars but not table names — typing WHERE x = won't pollute the popover with the 47 base tables.

6a.3 Variable-value preview

Variable completions show the current value next to the name. Numbers and short strings inline; complex values (range, row, list) show their shape. Hovering a var entry expands the full value in a side card without inserting (same shape as the popover from §2). This solves the most common pre-flight question: “is $gc_overview.brush empty right now?” — the answer is in the completion list.

6a.4 Snippets

A small fixed list of cross-cutting snippets is folded in. They fire on prefix match in the statement-start position only — they don't pollute mid-expression contexts:

  • brush-filter → WHERE startTime IN $gc_overview.brush (uses the focused cell's alias)
  • top-n → ORDER BY $1 DESC LIMIT $2
  • histogram → SELECT $1, COUNT(*) FROM $2 GROUP BY 1 ORDER BY 1
  • join-on-thread → JOIN $1 ON $1.threadId = $2.threadId

Snippets carry tab-stops ($1, $2) that the editor walks with Tab. Power users add their own snippets under ⌘, → SQL snippets; they persist per-workspace.

6a.5 Why this matters

Without completion, every cell starts by alt-tabbing to the schema sidebar (§0b) to remember a column name, then back to the editor. That's the most expensive sub-second cost in the write-a-cell loop. Schema completion alone removes that round-trip; var completion makes the live-coupling story (§5) discoverable without reading docs — the user starts typing $ and sees what's in scope, including its current value.

§7aPrompt language — typed grammar, local model, 🪄 button §10 · iter-10

The thing the user types into the chat input and into the 🪄 suggest plot button on every SQL fence. One sigil (@), seven verbs, five target kinds, formally typed. The chat input is no longer a <textarea> — it is a CodeMirror editor whose mode is the grammar below, with three-tier autocomplete backed by a ~25M-param ONNX model that runs entirely in the browser.

The grammar (EBNF)

A prompt is verb? target* prose? constraint* output-form?. Targets are always resolved before the prompt is sent — no silent guessing. 

prompt        = verb? target* prose? constraint* output-form?

verb          = "plot" | "table" | "filter"
                | "explain" | "fix" | "extend" | "summarize"

target        = "@" target-body
target-body   = cell-ref | view-ref | column-ref | var-ref | schema-ref

cell-ref      = "#" INT          ; @#5
              | IDENT                ; @gc_overview
view-ref      = IDENT                ; @last_5_min  (VIEWS panel)
column-ref    = IDENT "." IDENT      ; @gc_pauses.duration_ms
var-ref       = ("$" | "$$") IDENT ("." IDENT)*  ; @$gc_overview.brush, @$$theme
schema-ref    = "schema"            ; @schema  (meta-target)

prose         = .*                   ; free NL, fed to model verbatim
constraint    = "where" predicate     ; where @$brush from @#1
              | "binned by" duration ; binned by 10ms
              | "limit" INT           ; limit 100
              | "joined with" cell-ref ; joined with @#4
output-form   = "as" plot-type        ; as histogram
              | "into" cell-ref       ; into @#9
              | "into" "new"          ; into new

Constrained decoding — why plotForSql output is always parseable

Free-decoding a model trained on plot DSL still hallucinates: a stray ], a missing ", a plot type the grammar doesn't know. Constrained decoding masks the model's logits to the set of currently legal next tokens given the plot-DSL grammar — sampling can only choose from grammar-valid moves. The output is always a parseable AST; the only question is whether it's a good plot. 

// pseudo-implementation
function decodeStep(state, logits, grammarState) {
  const legal = grammarState.nextTokens();      // e.g. ['{', 'line', 'bar', 'histogram', …]
  for (const [tok, idx] of tokenizer.entries()) {
    if (!legal.has(tok)) logits[idx] = -Infinity;    // mask
  }
  const next = sample(logits, { topK: 3, temperature: 0.7 });
  grammarState.advance(next);
  return next;
}

Implementation note: the plot DSL is a regular-ish grammar with bounded nesting (row/col/+ composition + clause-tail). The grammar state machine is small enough (~30 states) that the legal-tokens computation is per-step O(1) after a one-time precompute of token→state edges.

Why custom instead of an LLM API

  • Privacy. The model never leaves the browser. The 🪄 button works regardless of the chat panel's chat.data_access: toggle — there's nothing to gate.
  • Latency. 50ms keystroke completion is unreachable over a network. A network round-trip is 100ms in the best case; an LLM API is 500ms in the median.
  • Cost. Free at inference. The training cost is a one-time investment, amortised over every user.
  • Offline. The author can be on an airplane and the prompt language still works fully.
  • Specialisation pays. A general 7B model spends most of its capacity on language it never sees here. A custom 25M model on a domain corpus matches or beats it on JFR-shaped queries while being ~280× smaller and ~50× faster.
  • External LLMs are still on the menu — via the chat panel (§7, iter-11) with the IAiProvider interface. Two paths, one grammar; the user picks per-prompt.

8a.2 Result caching with quantized $-keys (plan §8.2)

The cache key for a SQL run is hash(sql_text, table_versions, var_bindings). Two of those terms change on every mousemove: the brush x0/x1 are continuous floats. Verbatim floats produce a miss on every tick. The fix is to quantize the variables before hashing — round the brush to a granularity matched to the consumer's display resolution.

Without quantization

key(12:30:00.061, 12:35:11.124)  miss
key(12:30:00.082, 12:35:11.130)  miss
With quantization (50ms grid)
// rounded → same key for 50ms windows
qkey(12:30:00.000, 12:35:11.100)  miss
qkey(12:30:00.000, 12:35:11.100)  HIT
qkey(12:30:00.000, 12:35:11.100)  HIT

8a.3 Materialization tiers — the auto policy (plan §8.3)

Cross-cell views (-- @ alias) are TEMP VIEWs by default — DuckDB plans them on every query. For hot views in a brush-driven consumer chain this is wasted work. Three tiers, picked by an auto policy unless the user overrides:

TierStorageRefreshedCostWhen auto picks it

materialize: incrementalTEMP TABLE + delta tracking append-only on upstream growth full result size + small overhead per insertcell is on a streaming JFR source (phase E)

--- (cell frontmatter)

materialize: true      # force RAM
materialize: false     # forbid — author cares about RAM more than speed

When auto picks true, the cell head shows ↻ rematerializing while the table refreshes; a small chip ▦ 240MB · 50k rows shows the RAM cost once steady-state. Clicking the chip explains the decision (which chains triggered it, the p95 it's avoiding).

8a.4 Predicate push-down across chains (plan §8.4)

8a.5 Cascading cancellation (plan §8.5)

User drags the brush fast: 60 mousemoves per second, each writes the panel's $<cell>.brush, each could trigger a chain re-run. Without cancellation the system is a flood. Iter-8 uses one AbortSignal per gesture and propagates it through the dep graph:

// each consumer SQL run is launched with this signal
duckdb.run(sql, { signal: currentController.signal }) // → DuckDB-WASM cancelPendingQuery on abort

8a.9 Why this matters — the perf story end to end

  • Quantized caching turns a 60Hz gesture into ~5 cache misses/second instead of 60. Every consumer sees ~95% hits during a steady drag.
  • Materialization trades RAM for CPU when a view is on a hot path; the auto policy means most users never set the flag.
  • Push-down moves the filter to the source, collapsing intermediate row counts; the source cell's chip makes the rewrite visible so the user is never confused about why their plot looks different.
  • Cascading cancellation means rapid gestures don't queue work; only the most recent gesture's chain runs to completion.
  • Always-on perf surface means slow cells are visible without opening a profiler; the inspector turns "why?" into a one-click answer.

8a.10 Long-running query UX

Most SQL on a parsed JFR completes in < 50 ms. Some doesn't — a full-scan over 23M execution samples can take 8 s; a regex over an event-name column can take 30 s. The cell surface escalates feedback as time passes so the user is never wondering whether the runtime is alive.

Without an explanation of why a query is slow, the only escape hatch is "wait or cancel" — both of which give the user no new information. ⌥A opens a right-side drawer with one row per timestamped event in this session. Distinct from the chat audit log (which is per-cell, persisted in last_ai_session:) and from the issues panel (which is a current state, not a history). The activity feed is session-only; it does not persist.

⌥A · activity feed (session-only)

10a.3 Time travel from the activity feed

Clicking a row offers “restore state at this moment” — the snapshot of all live-vars at that timestamp is loaded into the runtime. Cells re-run against the restored state. This is distinct from the share-URL (§10) which captures one snapshot at share-time; the activity feed captures every snapshot in this session. The restore action is itself logged as a new row in the feed; the undo stack treats it as a single step.

10a.4 Privacy & size

The feed lives in memory only — it is not written to disk and not included in the saved notebook file. It clears on tab close. A ring buffer caps it at 1,000 events; older events drop silently. If a user wants a persistent log, the chat audit log (§7b.4) is the place: it is per-cell and survives reload.

§10bCheckpoints & version history §IT12.7 · §IT18.11

Git is the right answer for permanent history; the notebook is plain markdown and a workspace in a real git repo gets per-commit history for free. But during a session — when a user wants to try a wild query, see it fail, and roll back without remembering what they changed — git is too coarse. Checkpoints fill the in-session gap: timestamped snapshots of the entire notebook source, stored in localStorage, listable and diffable from the activity feed.

10b.3 Restore & diff

Restore on a checkpoint replaces the in-memory notebook with the checkpointed source. Before applying, the current state is itself auto-checkpointed as "before restoring <name>" so the restore is reversible. Cells that were running cancel; the user is dropped into the restored state with all live-vars cleared (no time-travel here — for that, use the activity feed §10a.3).

Diff opens a side-by-side view: left is the checkpointed source, right is current. Cells are matched by alias when possible, by position otherwise; added cells are cyan, removed cells are red, modified cells have an expandable inline diff. This is the same differ used by §8 (format-on-save) — semantic, not just textual.

10b.4 Storage budget & eviction

Checkpoints share the workspace's localStorage quota with other state (theme, $$-globals, draft, format prefs). The runtime tracks total checkpoint size; on approaching 8 MiB or 80% of the available quota it warns: "checkpoint storage near limit — oldest manual checkpoint will rotate in N more saves." Auto-checkpoints rotate silently; manual ones rotate only with explicit user acknowledgement.

10b.6 Why this matters

Without checkpoints, a user who is two queries deep into a wild rewrite has nowhere to go but ⌘Z and hope. Undo runs out of grain at some point; checkpoints don't. The discoverability cost is low (one new tab in a drawer the user already opens for the activity feed) and the rescue value is high — once a user has restored a checkpoint and recovered an hour of accidental damage, the feature has paid for itself many times over.

§10cRedaction — PII control on share & export §4.5 plan · §IT18.6

JFR recordings routinely contain identifying strings: thread names like http-nio-8080-exec-42 [user:alice@corp.io], hostnames in socket_read.remoteHost, exception messages with file paths, SQL statements with literal IDs. The moment a user clicks share or export, those strings leak. The redaction layer intercepts every outbound path — share URL fragment (§10), download PNG / CSV / SQL / notebook (§4a.2.3, §10b.2), agent context window (§7) — and asks the user once, per recording, what to scrub.

10c.1 The redaction modal

Opening on first share or export (or via ⌘⇧R), the modal lists every string-typed column across every loaded table, with three sample values, the distinct count, and a per-row toggle: keep, hash, or mask. Settings persist per-recording in localStorage under the recording's content hash, so a user who configures redaction once doesn't see the modal again for the same .jfr.

10c.2 The two transforms

ActionTransformReversible?Use when
✓ keep identity — Low-cardinality categorical (GC cause, event kind) where the value is itself the analysis.
⊕ hash SHA1(recording_salt || value)[:8], presented as #a3f2c190. No, but stable: same value always hashes the same within a recording. You need to group by the column (e.g. CPU-by-thread) but the actual names are sensitive. Plots and aggregates still work.
✕ mask Constant string <redacted>. No, lossy. The column adds no analytical value but contains free-form PII (exception messages, request URLs with IDs).

The salt is per-recording and never leaves the browser. Two shares of the same recording use the same hash mapping (collaboration works); two different recordings cannot have their hashes cross-referenced (cross-leak prevented).

10c.3 Where redaction applies

Outbound pathBehaviour
Share URL (§10) Any $<cell>.brush / $<cell>.zoom values embedded in the fragment are transformed in place: a hashed thread name in #brush.thread=… becomes #a3f2c190. The recipient sees the same hash; the link still scopes correctly.
PNG / SVG export (§3b.6) Axis labels, legend entries, tooltip ghosts, and annotations are re-rendered with the transformed values before the bitmap is generated. The user sees a redacted preview before the file leaves the browser.
CSV / Parquet / SQL export (§4a.2.3) Redaction is applied at the DuckDB query layer: the export query is rewritten to wrap affected columns in sha1_redact(col) or '<redacted>'. The user can preview the first 10 rows of the redacted output in the export dialog.
Notebook bundle export (§10b.2) Cells and prose are scanned for hard-coded sensitive values (anything that appears in a masked column's distinct list) and replaced with the chosen transform. A diff shows the user every substitution before the bundle is generated.
Agent context (§7) Every sample value, schema row, and sample_table response sent to the model is pre-redacted. The agent never sees raw values from masked or hashed columns — its suggestions reference the hashed form, which the user can map back locally.
Activity log download (§10a.2) Same as notebook export: hard-coded values in cell snapshots are scrubbed.

10c.4 The redaction badge

Once redaction is configured for a recording, a small 🛡 redacted (4) pill appears in the status bar (right of the workspace label, §0a). The number is how many string columns are not keep. Clicking the pill reopens the modal. The pill is cyan-bordered if redaction is active, gray-bordered (🛡 not configured) if the user has never opened the modal — clicking the gray pill opens it for the first time without requiring a share-or-export trigger.

10c.5 What redaction does not do

LimitationWorkaround
It does not scrub numeric columns. A timestamp, memory address, or duration can still be identifying in combination. If a numeric column is sensitive, the user must drop it pre-export via a SQL projection.
It does not re-analyse plot pixels for residual PII (e.g. a label that was burned into an annotation before the redaction config was set). Annotations capture the transformed values at render time; if added before configuration, the user is warned and asked to re-render.
Hashing is deterministic per recording but not across recordings; you cannot correlate two shared recordings by hashed thread name. This is intentional. To correlate intentionally, the user can set an explicit shared salt in workspace settings.

10c.6 Why this matters

JFR data is often pulled from production, which means the friction between “I want to share this finding with a colleague” and “but my recording has user IDs in it” is the moment users either give up on sharing or commit a privacy mistake. A modal with sensible defaults — keep low-cardinality categoricals, hash mid-cardinality identifiers, mask free-form text — turns a privacy hazard into a one-click decision, and the per-recording memory means the cost is paid once.
