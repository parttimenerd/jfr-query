## Bug 1: Duplicate heading "JFR SQL Notebook" — `<h1>` in Topbar and `<h2>` in WelcomeCell
**Found by:** testing agent
**Commit:** `2d8a662`
**Test:** `tests/e2e/99-edge-cases.spec.ts` — Playwright strict-mode violation on any test that uses `getByRole('heading', { name: /JFR SQL Notebook/i })`
**Severity:** 🟡 Warning

**Reproduction:**
1. Go to `/`
2. Open DevTools and inspect the heading hierarchy
3. Observe two headings with the same text: `<h1>JFR SQL Notebook</h1>` inside `<header>` and `<h2>JFR SQL Notebook</h2>` inside `[data-testid="welcome-cell"]`

**Expected:** The page title ("JFR SQL Notebook") should appear once as the `<h1>` in the Topbar. The WelcomeCell should use a different, more specific heading (e.g. "Get Started" or "Welcome") or omit the h2 entirely since the Topbar already names the app.

**Actual:** `getByRole('heading', { name: /JFR SQL Notebook/i })` resolves to 2 elements:
- `<h1 class="...">JFR SQL Notebook</h1>` (Topbar, `src/components/shell/Topbar.tsx`)
- `<h2 class="...">JFR SQL Notebook</h2>` (WelcomeCell, `src/components/shell/WelcomeCell.tsx`)

This breaks Playwright strict-mode selectors, confuses screen-reader users (two landmarks with the same name), and pollutes the heading outline.

**Suggested fix:** Change the `<h2>` in `WelcomeCell.tsx` to something distinct, for example "Get Started with JFR SQL Notebook" or just "Welcome". Alternatively, make the WelcomeCell heading omit the product name entirely.

## Bug 4: Color contrast too low in CodeMirror oneDark theme — SQL keywords below 4.5:1 AA (WCAG 1.4.3 — Serious)
**Found by:** testing agent
**Commit:** `2d8a662`
**Test:** `tests/e2e/99-edge-cases.spec.ts` — "no WCAG 2.1 AA violations when notebook is open"
**Axe rule:** `color-contrast` (WCAG 2 AA, WCAG 1.4.3)
**Severity:** 🟡 Warning

**Reproduction:**
1. Go to `/` with dark theme active (default)
2. Click "Open example notebook"
3. Observe the SQL text in the CodeMirror editor (e.g. `events`, `type` appear in a coral/pink color)
4. Run axe — `color-contrast` fires on `<span class="ͼ6">` elements (SQL identifiers in oneDark)

**Expected:** All text in the editor should meet WCAG AA minimum contrast ratio of 4.5:1 for normal-sized text.

**Actual:** 
- Foreground: `#e06c75` (coral/pink — SQL identifiers in oneDark)
- Background: `#282c34` (oneDark editor background)
- Contrast ratio: **4.38:1** (required: 4.5:1)
- Affected elements: `<span class="ͼ6">events</span>`, `<span class="ͼ6">type</span>` (SQL identifier tokens)

The `oneDark` theme from `@codemirror/theme-one-dark` is a third-party theme that does not meet WCAG AA for some token colors.

**Suggested fix:** Either:
1. Replace `oneDark` with a WCAG-compliant CodeMirror theme (e.g. a custom theme derived from the app's own design tokens), or
2. Override the specific failing token colors with WCAG-compliant alternatives that still maintain visual distinction. The coral `#e06c75` needs to be shifted to approximately `#e87c86` or brighter to reach 4.5:1 on `#282c34`.

Note: The light theme does NOT reproduce this particular violation — it is specific to the dark-mode CodeMirror editor.

## Bug 5: DuckDB WASM worker served with wrong MIME type — query execution never completes (🔴 Critical)
**Found by:** testing agent
**Commit:** `1108c62 style: auto-fix lint+prettier after M-B2`
**Test:** `tests/e2e/99-edge-cases.spec.ts` — "DuckDB worker starts but stays running — worker MIME type bug reproduces"
**Severity:** 🔴 Critical

**Reproduction:**
1. Build with `npm run build`
2. Serve with `npm run preview`
3. Open the app, click "Open example notebook"
4. Click "Run" on any SQL cell
5. Status shows "⟳ running…" forever and never changes
6. Browser console shows: `[DuckDBClient] Worker error: Event`
7. Verify: `curl -sI http://localhost:4173/assets/worker-*.ts | grep content-type` → `Content-Type: video/mp2t`

**Expected:** The DuckDB WASM worker should be built as a `.js` file and served with `Content-Type: application/javascript`. The browser should load the worker successfully and queries should execute.

**Actual:**
- Vite builds the worker with a `.ts` file extension: `/assets/worker-BJ1u8s8d.ts`
- The preview server (and production servers) serve `.ts` files as `video/mp2t` (MPEG-2 Transport Stream)
- The browser rejects the worker: `new Worker(url, { type: 'module' })` fails with a MIME error
- `worker.onerror` fires and logs `[DuckDBClient] Worker error: Event` 
- The `this.ready` promise never resolves and all queries hang forever at `await this.ready`
- Cell status gets stuck at "⟳ running…" with no way to recover without reload

**Root cause:** The worker URL is constructed in `src/context/DuckDBContext.tsx` as:
```typescript
new URL('../services/duckdb/worker.ts', import.meta.url)
```
Vite's worker bundler preserves the `.ts` extension in the output hash name. The `.worker.ts` → `.js` transform that Vite does for `?worker` imports is not applied when using `new URL()` syntax with `worker: { format: 'es' }`.

**Suggested fix (two options):**

Option A — Use Vite's `?worker` import syntax which correctly outputs `.js`:
```typescript
import DuckDBWorker from '../services/duckdb/worker.ts?worker';
// Then:
this.worker = new DuckDBWorker();
```

Option B — In `vite.config.ts`, set the worker rollup output to use `.js` extension:
```typescript
worker: {
  format: 'es',
  rollupOptions: {
    output: {
      entryFileNames: '[name]-[hash].js',  // force .js extension
    },
  },
},
```

Option A is cleaner and is the idiomatic Vite pattern.

## Bug 6: DepGraphSource crashes with "Cannot read properties of undefined (reading 'cells')" when `graph` prop injected without `notebook` prop (🔴 Critical)
**Found by:** testing agent
**Commit:** `0aaf745 fix(v2): M-B5 refinements`
**Test:** `tests/e2e/depGraph/overlay.e2e.spec.ts`, `overlay.a11y.spec.ts`, `overlay.visual.spec.ts` — all fail at `?fixture=depGraphCanonical`
**Severity:** 🔴 Critical

**Reproduction:**
1. Go to `/?fixture=depGraphCanonical`
2. Observe error in console: `TypeError: Cannot read properties of undefined (reading 'cells')`
3. The ErrorBoundary catches it and shows the crash UI
4. The depGraph overlay never renders and `Meta+g` does nothing
5. Confirmed in tests: `expect(page.getByTestId('depgraph-overlay-dialog')).toBeVisible()` times out

**Expected:** When the `graph` prop is injected directly into `DepGraphSource` (Playwright fixture seam), `computeDepGraph` should NOT be called because `notebook` is `undefined`. The component should use `graphProp` directly.

**Actual:**
```tsx
// src/components/depGraph/DepGraphSource.tsx
const computedGraph: DepGraph = useMemo(
  () => computeDepGraph(notebook!, effectiveRuntime),  // ← crashes: notebook is undefined
  [notebook]
);
const graph: DepGraph = graphProp ?? computedGraph;  // graphProp is provided, but computedGraph runs first
```
`useMemo` runs unconditionally on render. When `graphProp` is provided, `notebook` is `undefined` but `notebook!` asserts it non-null, causing the crash.

**Suggested fix:** Guard the `useMemo` computation:
```tsx
const computedGraph: DepGraph | null = useMemo(
  () => (notebook ? computeDepGraph(notebook, effectiveRuntime) : null),
  [notebook]
);
const graph: DepGraph = graphProp ?? computedGraph ?? { nodes: [], edges: [] };
```
Or equivalently, skip the `useMemo` when `graphProp` is provided:
```tsx
const graph: DepGraph = graphProp ?? useMemo(
  () => computeDepGraph(notebook!, effectiveRuntime), [notebook]
);
```
(Note: hooks can't be called conditionally, so the first approach is correct.)
