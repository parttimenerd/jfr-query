Full design — three phases

Click each phase to expand. All three together = "the good pal".

PHASE 1 Visual refresh + embedded cells
  • Redesigned message bubbles — darker bg, avatar dot, asymmetric radii, code pills
  • AI can embed any cell type inline: mini chart, full chart, flame graph, data table, SQL results
  • Each embedded cell has a cell header (type + query) + ↗ Add to notebook button
  • Multiple cells per message, text flows above and below each
  • Model badge in header showing active provider + local/cloud indicator
  • Improved input area — unified rounded card
  • Variables fully in scope: AI sees current variable state, can reference vars in generated SQL, tool calls can update vars
How cells embed: AI response contains a special :::cell markdown fence with type + SQL + plot config. ChatMarkdownView detects it, renders the live cell component (reusing PlotRenderer / DataTable). "Add to notebook" promotes it via the existing onAddCell callback.
PHASE 2 AI-decides visualization + data access
  • AI decides when to visualize — no explicit trigger needed. System prompt instructs it to embed cells when data would be clearer as a chart or table
  • AI can run its own queries — new query_data tool: AI writes DuckDB SQL, gets results back, can embed them or just use values in its answer
  • Uses current cell results as context automatically (existing visibility system: no-data / sanitized / full)
  • Variable values included in context — AI can reference $threshold, write SQL with WHERE pause_ms > $threshold
  • Schema always available — AI knows table names and column types
Data sharing setting: Existing aiDefaultVisibility ('no-data' | 'sanitized' | 'full') already controls this. Phase 2 makes it prominent in the UI and adds a per-session override toggle in the chat header.
PHASE 3 Local model routing
  • LocalAiProvider already exists — OpenAI-compatible (Ollama, llama.cpp, LM Studio). Phase 3 wires it into chat properly
  • Routing logic: when a local model is configured, simple questions (schema lookup, short SQL, variable reads) go local; complex reasoning + visualization goes cloud
  • Local model is the privacy-safe default — no data leaves the machine unless the user opts in via the visibility setting
  • Model badge in header shows local vs cloud for the current message being processed
  • Settings panel: local model URL, model name, routing threshold toggle ("prefer local when possible")
  • Graceful fallback: if local model is slow or unavailable, routes to cloud with a notice
Routing heuristic: message length + tool count + data visibility. Short message + no tools + no-data visibility → local. Any tool call or full visibility → cloud. User can override per-session.
